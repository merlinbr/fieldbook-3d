01 / Where are you starting?

Q&A is for uncertainty. It is not a ritual to repeat before every implementation.

An idea with open questions

Clarify before building.

Requirements, expected behavior, scope, or design choices are still unclear. Start a focused interview in the repository.

/skill:grill-with-docs Describe the feature you want to explore.

Small feature? The interview can be short. Large feature? Resolve the decisions before writing the spec. Vocabulary and architectural decisions are retained in glossary/ADR docs when appropriate.

A clear small feature or ready ticket

Go straight to implementation.

The desired behavior, scope, and acceptance criteria are understood. No new spec or ticket breakdown is needed just for ceremony.

/skill:implement GitHub issue #123. Ask about unresolved requirements before coding.

The skill assumes specified work; it does not include a mandatory interview. The agent can ask targeted questions when a consequential detail is missing.

A bug with an unclear cause

Diagnose, don’t guess.

A bug report is evidence of a symptom—not proof of the cause. For hard, intermittent, or regression bugs, reproduce the failure and investigate first.

/skill:diagnosing-bugs Describe the failure and how to reproduce it.

A small, well-understood fix can go to implement. Small size alone does not make an unknown cause implementation-ready.

A completed spec already exists

Enter the flow here.

Do not restart the interview. For a multi-session build, turn the existing spec into tickets. For a small build, implement against the spec directly.

/skill:to-tickets Use the completed spec. Propose the breakdown for my review before publishing.

Prefer the session that produced the spec. In a fresh session, pass its file path or issue reference and any relevant decisions.

02 / The larger-feature flow

For work that needs multiple implementation sessions. Each command is a separate step—not an automatic chain that starts coding when a spec is published.

  1. 01 · CLARIFY

    Q&A + decisions

    /skill:grill-with-docs

    Settle what the feature should do, its constraints, and meaningful design choices.

    Output: shared understanding; glossary terms and ADRs as needed.

  2. 02 · CAPTURE

    Write the spec

    /skill:to-spec

    Synthesize the conversation: problem, solution, user stories, implementation decisions, testing decisions, and exclusions.

    Output: a spec published to the configured tracker.

  3. 03 · DECOMPOSE

    Approve the tickets

    /skill:to-tickets

    Propose end-to-end slices, acceptance criteria, and genuine blocking dependencies. Review the breakdown before publication.

    Output: self-contained tickets that can be verified individually.

  4. 04 · BUILD

    Implement a ready ticket

    /skill:implement

    Work a ticket whose blockers are complete. Use TDD where possible, run checks, review the diff, and commit.

    Output: implemented and verified behavior.

The short route: Q&A → clear scope → implement in the same conversation. A small, fully specified ticket can enter directly at step 4.

If a design question needs runnable evidence, detour through prototype and bring the findings back. For a huge effort whose route is still foggy, use wayfinder before spec and tickets.

03 / Where did the implementation plan go?

Your previous flow

Spec → plan → implementation

A separate implementation plan describes how the code will be changed.

Matt’s larger-build flow

Spec → tickets → implementation

Technical decisions live in the spec; the approved ticket breakdown supplies deliverables, acceptance criteria, and execution dependencies.

Planning still exists. It is represented by decisions and tickets, rather than a required file-by-file plan.md. The implementer still reads the code and works out concrete edits.
  • Spec: what to build, why, technical agreements, test seams, and what is out of scope.
  • Tickets: independently demoable or verifiable vertical slices—not “all backend first, all UI later.”
  • Dependencies: work any ticket whose blockers are complete; independent tickets need not be artificially serialized.
  • Grilling: clarification, not ticket splitting. to-tickets performs the breakdown.

05 / Practical notes

Stay in the discussion session through ticket creation.

Keep clarification, spec synthesis, and ticket breakdown together while practical. Start each ticket implementation with fresh context once the ticket is self-contained. If you must switch sessions earlier, provide the spec and relevant decision records instead of relying on memory.

Our setup uses GitHub, not local spec files by default.

Specs and tickets are published as issues in merlinbr/fieldbook-3d. The conventions are in docs/agents/issue-tracker.md, triage-labels.md, and domain.md. Setup is already complete; it records the five default triage label names but does not itself create those labels on GitHub.

Grill-with-docs versus grill-me is about context, not feature size.

Use grill-with-docs inside a repo: it retains resolved vocabulary and architectural decisions. Use grill-me for a stateless discussion outside a working directory. A small feature can still benefit from a short grill-with-docs session.

Implement does not mean “automatically merge and push.”

The installed implement skill calls for TDD where possible, typechecking and tests, code review, and a commit to the current branch. Merging and pushing are separate repository actions; request those explicitly when wanted.

Other entry points are optional, not mandatory ceremony.

triage processes raw incoming reports into agent-ready work; tickets already produced by to-tickets do not need another triage pass. ask-matt helps choose a route. retro reflects on a completed build to improve the agent environment.
